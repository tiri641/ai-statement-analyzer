# ループエンジニアリング開発

計画からレビューまでのフィードバックループを明確にしながら、規模のあるソフトウェア変更を実装するときに使用する。ユーザーが指定したスコープ、ブランチ方針、テストフレームワーク、デプロイ境界を維持する。

## 基本ループ

1. ファイルを変更する前にリポジトリを確認する。
   - 現在のPlan、関連する設計文書、テスト、パッケージスクリプト、ブランチ状態、作業ツリーを読む。
   - 現在のPhaseと、そのPhaseでの最小の成果物を特定する。
   - 作業前にリポジトリ固有のエージェント指示を確認する。

2. 実装前にPlanを作成または更新する。
   - 目的、非目的、設計判断、変更対象ファイル、テスト戦略、運用影響、完了Gateを記載する。
   - プロジェクトがPhase PlanやトップレベルPlanを使う場合は、Planをリポジトリに残す。
   - 同時に進行中にするPlan項目は1つだけにし、証拠が得られるたびに状態を更新する。
   - 不足している判断がスコープ、安全性、外部動作を大きく変える場合だけ質問する。それ以外は、記録可能で可逆的な仮定を置いて進める。

3. 作業ブランチを作成する。
   - ユーザーがベースブランチを指定した場合は、ブランチ作成前に指定どおり更新する。
   - 指定されたベースから専用ブランチを作成し、編集前に現在のブランチとベースのコミットを確認する。
   - 変更中の作業ツリーにある無関係な既存変更を保持する。

4. TDDで実装する。
   - Red: 期待する動作を表す最小のテストを追加し、意図した理由で失敗することを確認する。
   - Green: テストを通す最小の変更を実装し、機能を広げない。
   - Refactor: テストをGreenに保ちながら、名前、境界、重複、ドキュメントを整理する。
   - 障害動作では、状態遷移と外部ACK／副作用の境界を両方テストする。
   - 必要に応じて、競合条件、再試行、古い所有権、不正入力、秘密情報・エラー文の漏洩に対する回帰テストを追加する。

5. 段階的に検証する。
   - Red／Greenの各スライス後に、対象を絞ったテストを実行する。
   - 全テスト、リポジトリが要求する結合テスト、型チェック、ビルド、生成物／合成チェック、プロジェクトに適した形式／Diff checkを実行する。
   - 実行した正確なコマンドと成功件数をPhase記録またはPR本文に残す。
   - 必須チェックを省略した場合は成功と報告せず、環境上のBlockerとして別に報告する。

6. 引き渡しを準備する。
   - 未追跡ファイルを含む完全なDiffを確認し、スコープ、セキュリティ、マイグレーション安全性、運用デフォルト、ドキュメントの整合性を確認する。
   - 意味のまとまったコミットメッセージでコミットする。Pushはユーザーが明示的に依頼した場合だけ行う。
   - ユーザーがPR作成または引き渡しを依頼した場合だけ、指定されたベースに対してPRを作成し、簡潔な概要、設計・運用メモ、TDDの証拠、既知のフォローアップを記載する。

7. 独立したレビューのループを実行する。
   - ユーザーがエージェントレビューを依頼した場合、またはワークフローが明示的に要求する場合は、別のレビューエージェントを使う。
   - 実際の最終Diff／Commitをレビュー担当へ渡し、ファイル／行番号付きで重要度分類された指摘を求める。想定する結論を事前に伝えない。
   - Blocking／Highの指摘は引き渡し前に修正する。Mediumの指摘はスコープとリスクで評価し、意味のある回帰にはテストを追加する。
   - 修正後は対象テストと全検証を再実行する。Pushはユーザーが明示的に依頼した場合だけ行い、更新後のDiffの最終レビューを依頼する。
   - 最終レビューでBlocking／Highの指摘がなく、必須の検証Gateがすべて通ったら停止する。外部認証、ネットワーク、レビュー基盤が引き渡しを妨げる場合は、正確なBlockerと最後に成功したローカル証拠を報告する。

## 重要な不変条件

- 実装前にPlanを作成し、作業の進行に合わせて更新する。
- ブランチはユーザーが選んだベースから作成する。
- 実装完了と判断する前に、テストで期待する動作を示す。
- 設計で明示されていない限り、再試行可能な失敗をACKしたり、終端状態へ変換したりしない。
- 恒久的な失敗は、ACK前に安全で許可リスト化された結果を永続化する。
- 外部副作用と破壊的操作には、ユーザーによる明示的なScopeが必要。PR依頼は通常のCommit／Push／PR手順を許可するが、無関係なDeployやProduction変更までは許可しない。
- プロジェクトで明示的に必要とされない限り、秘密情報、ユーザーの生データ、プロバイダー認証情報、内部例外の詳細をテスト、ログ、PR、公開API、永続化する失敗メッセージへ入れない。
- 過去のPhase記録は当時の事実として正確に保ち、動作が変わった場合は現在状態のドキュメントを更新する。

## コミュニケーション形式

開始時に選択したPlan／ブランチ／TDD／レビュー方針を示す。作業中は意味のある状態変化とBlockerだけを報告する。引き渡し時には次を含める。

- 作成した場合は結果とPR URL
- ブランチとコミット
- テストなどの検証コマンドと結果
- レビュー指摘と修正済みかどうか
- 残存リスク、フォローアップ、外部設定手順

最終報告は簡潔で自己完結させる。
